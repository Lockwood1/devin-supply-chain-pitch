The work nobody budgets for

Configuring the WMS is the system integrator's job, and they're good at it. But a warehouse transformation lives or dies on engineering work that sits between systems — work that rarely has a named owner or a real line in the budget.

01Integrations

ERP, carriers, 3PLs, EDI partners. Every interface into the old WMS has to be rebuilt, remapped, and retested — across every site in the network.

02Data migration & cleansing

Item masters, locations, inventory balances, customer and vendor records. Bad data doesn't fail in the project plan. It fails on cutover weekend.

03Undocumented legacy code

Years of customizations, bolt-ons, and reports nobody wrote down. Some of them still do something important. Nobody is sure which.

04Regression testing

Every mock cutover and every go-live needs the same flows verified end to end. This is the work that quietly slips when the timeline tightens.

05The post-go-live backlog

The ticket queue lands on the same engineers who just ran the migration — while the ERP program is already staffing up behind them.

One investment, two migrations

The ERP replacement inherits whatever the WMS project leaves behind. With Devin in the code, most of it becomes an asset instead of a liability.

Documentation becomes the spec

What Devin writes down about how the legacy system actually behaves becomes the requirements document for ERP integrations — not a wiki page that goes stale, but reviewed, merged documentation.

Integration code carries forward

Carrier, 3PL, and EDI interfaces don't disappear with the old WMS. They get repointed at the new ERP — remapped, not rebuilt from scratch.

Test suites get rerun, not rebuilt

The regression suite that protects the WMS cutover protects the ERP cutover. Same network, same flows, same proof before go-live.

Knowledge doesn't walk out the door

System knowledge ends up in code and documentation your team owns — not in people's heads that leave when the project ends.

Straight answers

The objections I'd expect — answered directly.

“Devin doesn't replace our integrator.”
Correct — and it shouldn't. The integrator owns business process design and WMS configuration. Devin works alongside them on the code-level engineering around it: the integrations, data scripts, and tests that otherwise show up as change orders.
“We can't give an AI access to our systems.”
You don't hand over the keys. Every change arrives as a pull request your engineers review and approve before anything merges. Access can be scoped — Cognition supports RBAC, SSO, and fine-grained access controls, doesn't train on enterprise customer data, and publishes SOC 2 and ISO 27001 on its public security page, with a Trust Center for the details.
“Our code is too old — or too custom.”
That's the case for it, not against it. Undocumented legacy code is exactly where automated code understanding pays back first — and it's where the risk of losing knowledge to retirement and attrition quietly sits. (Nubank's migration started from an 8-year-old, 6-million-line monolith.)
What Devin does not do
It doesn't click through vendor setup screens, and it doesn't own business process design. Those stay with the integrator and your team — where they belong.

A bounded way to start

Not a platform decision. One integration, one engineer overseeing, a few weeks, clear exit criteria.

Pilot: document and test one integration

Scope
One bounded interface — for example, the WMS–ERP inventory sync, or a single carrier / EDI connection. Document how it actually behaves today, map the fields, write the validation tests.
Duration
Roughly four weeks, running alongside the program — never in its way.
Success criteria
Complete documentation of the interface as it really behaves. A repeatable validation suite your team can run before every mock cutover. Your engineers' sign-off on every pull request.
Exit criteria
If it doesn't produce docs and tests your engineers would sign, don't expand. If it does, the same pattern scales to the rest of the integration list — and into the ERP program.
